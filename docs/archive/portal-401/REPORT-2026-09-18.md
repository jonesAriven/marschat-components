## 2. portal 并发同账号「被踢」— 诊断与修复规格

证据：`verify/design/portal-401-diagnosis.md`（定稿诊断）、`portal-401-fix-spec.md`（实施规格）、`portal-401-e2-e4-findings.md`（E2/E4/E4b 实测）、`portal-401-handoff.md`（工程师交接单）、`portal-s3s4-defect-registration.md`（独立缺陷登记）。

### 2.1 根因口径（2026-09-18 13:15 更新 —— 含一条重要反转）

| 候选 | 状态 |
|---|---|
| **C1** 前端 token 窗口（请求压根没带 Bearer） | ❌ **未复现** —— E2 实测 **9/9 轮全部 `NO401`**（A 全程在线、B 全程未被触碰） |
| **C2** token 归属不符（`iss`/`typ` 非 portal） | ✅ **形态已证实** —— portal-server 日志 `拒绝跨应用 token` 共命中 **7 次，全部落在 `uri=/portal/api/sys/system/all`**（09:19:08 / 09:51:57 / 10:53:29 / 10:57:57 / **13:10:05 / 13:20:14 / 13:37:54**），分支 = `JwtInterceptor.java:42`（验签过但 `isIssuedByPortal()` 为假）。**具体 token 来源仍未定位**；⚠️ 见下方"真实用户影响未证实" |
| **C3** 身份守卫静默重授权（与 401 无关） | ✅ **E3 已证实形态** —— S3 失败时 `POST /portal/api/auth/sso/exchange` **根本没被发出**、停留 callback、`portal_token=null`、**全程 0 个 `/portal/api/**` 401** ⇒ 命中 `main.ts:65-67` 守卫跳转。**⇒ S3/S4 的失败与"硬踢 401"是两条不同链路** |

- **已确证硬缺陷（但与"硬踢"无因果）**：`AuthCenterService.refreshTokens` = 进程内 `Map<Long,String>`、**键 = userId 单槽、无锁**；
  SSO 路径写入 / legacy 路径消费；`removeRefreshToken` 在本地过期或刷新失败时把**非唯一键（null）当唯一键删除**。
  实证：portal-server 日志出现 `auth-center token 请求失败 400 invalid_grant` + `SSO 会话已失效` 共 3 次（03:33 / 04:45 / 08:46）。
  ⚠️ 但它产出的是 **HTTP 200 + `code:401`（不硬踢）** ⇒ **它是"硬踢"症状的红鲱鱼**，不能拿来解释真 401。
- **关键区分**：只有**真 HTTP 401** 才触发硬跳；业务 `body code:401` 走成功分支只 reject。全平台唯一 401 发射点 = 后端 `JwtInterceptor`（SC_UNAUTHORIZED）。
- **已证伪的历史成因**：portal / infra-monitor / kb-gateway 三把 HS256 密钥 **sha256 互不相同**（kb-ops 的为空串）
  ⇒ "与 infra 共用密钥"**对本次 4 次 401 不成立**，密钥分离已落地。
- **仍存在的可观测性缺口**：`JwtInterceptor.java:57`（无 Bearer / 验签失败）**当前不打日志** ⇒ 日志里 `未登录` 计数 = 0
  **不能**说明该分支没发生。这正是 E0 要补的洞。
- **我据 git 收窄的范围（只读）**：`isIssuedByPortal` 归属闸门由 **`512b8736`（09-15 02:31「Phase 10 密钥分离 + 接口闸门」）一次性引入**；
  `portal-server` 的 `JwtUtil.generateToken`（`JwtUtil.java:100-114`）**只有一条签发路径**，恒写 `iss` + `typ='portal'`
  ⇒ **当前 build 不可能自产"过验签但 iss/typ 不符"的 token**。来源只剩三种：`PORTAL_JWT_ISSUER` 环境值漂移（`application.yml:66` = `${PORTAL_JWT_ISSUER:marschat-portal}`，可覆盖）/
  "已换密钥、未带声明"的过渡 build / 测试 profile 里跨 build 存活的旧 token（portal JWT 有效期 24h ⇒ 只有 24h 窗口内才可能存活）。
  另：`27ca74df`（09-16 08:55「移除 SSO 免登短路 portal_reauth_once」）动过 SSO 重授权短路，已列为 S3/S4(C3) 的优先怀疑对象。
- 🔴 **【必须原样保留的诚实边界】"真实用户会被踢"至今未被证实。**
  - **全部**"硬踢 401"的观测（QA 的矩阵、架构师的 E1/E2/E3）**都来自自动化夹具**，没有一条来自真实用户路径。
  - **7 次命中按小时只落 3 个桶**（09 / 10 / 13 时），且**与自动化测试窗口一一对齐**；其中 **13:10:05 / 13:20:14 / 13:37:54 三次落在架构师自己的实验运行窗口内** ⇒ **高度疑似夹具自触发**（未定格）。
  - ⇒ **代码里那条"真 401 ⇒ 无条件硬跳"的机制是真的、可读代码验证；但它被真实用户触发的概率目前未知。**
    对外表述只能是"portal 存在一条会硬踢的 401 处理路径"，**不能表述为"portal 有并发被踢缺陷、真实用户会被踢"**。

## 8. 本轮测试脚本误判登记（避免后人重踩）

| # | 现象 | 真因 | 纠正 |
|---|---|---|---|
| 1 | portal 中心台表格 `loading: true` 持续 37s+，一度判为"表格永远转圈" | 采集时机在 lazy tab 组件 mount 后的加载窗口内；**独立时序采样（每 5s，共 65s）实测 `loading=false`、`rows=4` 全程稳定** → 产品无此问题 | 断言前必须等 `loading === false` 再采集，不能只等"按钮出现" |

## 9. 缺陷 D4 · activecode SSO 回跳错误落到 index.html（2026-09-19 独立发现）

**提交**：`37d291a0`（1 file, +39/-2，已提交未 push）

### 9.1 症状（用户原话路径）
SSO 单点登录后停在 `https://tools.marschat.online/activecode/index.html`（**激活码校验首页**，标题「激活码生成」），
而非管理后台 `https://tools.marschat.online/activecode/main.html`。

### 9.2 根因（实测，非推测）

`marschat-auth-core.umd.js` 的 `handleSsoCallback()` 末尾：

```js
const target = toSpaPath(config2, sessionStorage.getItem(SESSION_KEYS.redirect) || "/dashboard");
```

`toSpaPath()` 按 `redirectUri`（`/activecode/sso-callback.html`）推出 `base = /activecode`，
然后**把部署前缀剥掉** —— `/activecode/main.html` ⇒ **`/main.html`**。

**关键**：那套「剥前缀」口径是为 **Vue SPA + `router.push()`** 设计的（router 会自动补 base）。
而 **activecode 是 MPA**（多个真实 `.html` 页），落地走的是
`sso-callback.html:55` 的 `window.location.replace(真实路径)` —— 剥掉前缀后 `/main.html` 在服务端**不存在**。

### 9.3 证据链（curl 实测 nginx 兜底）

| 请求 | 结果 |
|---|---|
| `/main.html` | 302 → `https://tools.marschat.online/activecode/` |
| `/activecode/` | 302 → `https://tools.marschat.online/activecode/index.html`（200，标题「激活码生成」）|
| `/dashboard` | 302 → 同样兜底到 `/activecode/` |

⇒ `/main.html → /activecode/ → /activecode/index.html`，**与用户观察到的症状完全吻合**。

### 9.4 影响面判定（全局根治，避免打地鼠）

| 应用 | 落地方式 | 是否被影响 |
|---|---|---|
| **activecode** | `window.location.replace()`（MPA 整页导航）| 🔴 **是**（本次修复）|
| kb-web / kb-ops / infra-monitor / myfrp | `router.push(redirect)`（SPA，router 自动补 base）| ✅ 不受影响，剥前缀对它们**是正确的** |
| portal | BFF 服务端流，不走组件的 handleCallback | ✅ 不适用 |

⇒ **修复放在 activecode 的适配层 `sso.js`，不动公共组件** —— 改 `toSpaPath` 会波及上述 4 个 SPA 应用。

### 9.5 修复

`sso.js` 新增 `normalizeLanding()`，把组件返回值归一为**带前缀的真实路径**：
① 已带 `/activecode/` 前缀（含 `main.html#records` 深链）→ 原样；
② 组件兜底的 `/dashboard`、空值 → 回管理后台；③ 被剥前缀的 → 补回。

**一处修复覆盖两条路径**：首次登录 + **静默续期**（`renew()` 传的同样是带前缀的
`location.pathname`，回调时一样会被剥）。

`/main.html`、`/activecode/main.html`、`#records` 深链、`/dashboard`、空值、`null`、无前导斜杠等用例全覆盖。
