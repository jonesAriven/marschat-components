## 3 缺陷与订正

### 3.1 脚手架未知 flag 静默忽略（本轮唯一代码变更，已修 + 双向验证）

- **现象**：J1 用 `--out-dir /root/verify/r22/jout` 传参，实际 flag 是 `--out`；旧 `parseArgs` 对未知 flag **静默接受**（存入 `out['out-dir']` 后无人读），产物落到默认目录 `scaffold-out/`。**不报错、不失败**，只是目录不对 —— 与坑 #41/#42/#43 的「静默失效」同型。
- **修复**（`scripts/scaffold-app.mjs`）：`parseArgs` 增加已知 flag 白名单（`app-id` / `context-path` / `out` / `name` / `token-prefix`），未知 flag 立即报错退出并列出已知参数。
- **双向验证**：正常 `--out` → exit 0（11 产物 + 8/8 门禁）；`--out-dir` → exit 1 且报错精确；缺 `--app-id` → exit 1（原行为保持）。

### 3.2 mykng 宿主级 HAProxy 13306 层（环境注记，新登记 T-OBS-8）

- **事实**（原子层核实）：mykng 宿主跑 `/usr/sbin/haproxy`（systemd active，2026-08-22 起），`frontend *:13306 → backend mysql_cluster`，`balance first` + tcp-check，后端 node1(105:3306) → node2(182:3307) → node3(182:3308)。
- **对平台的影响 = 零**：应用数据源走 compose 网络别名 `platform-mysql`（= platform-mysql-1 容器 = GR node1），不经 HAProxy；GR 状态查询、读写、回归全部正常。
- **登记原因**：历轮回归基线与 `配置参考.md` §8 均未记录该入口，属**认知缺口非缺陷**。顺带纠正一处表述：`platform-mysql-1` 容器基础镜像虽是 `mysql:8.0`，但 `group_replication` 插件 **ACTIVE**（GR 不用 wsrep 插件，「无 wsrep」不是判据）。
- **处置**：`T-OBS-8` 待观察；后续文档补记 13306 入口时说明「旁路 failover 入口，应用默认不走」。

### 3.3 devtools 流水线 #872–#875 事件（环境噪声，已自愈）

- K3 核对时复见 #872 kb-ops-web / #873 kb-web / #874 infra-monitor-web / #875 portal-web 四条 clone ✅ 但 deploy ❌（`bash: 部署脚本: No such file or directory` + scp /tmp tar 不存在）。

- 维持 `T-OBS-7` 登记，低危待排期（建议 deploy 步骤加超时与并发互斥）。
