# 统一认证平台 · 应用接入架构审计报告

**主题**：应用接入是否满足「引入公共前后端组件 + 少量配置化即可接入」的目标
**审计对象**：`marschat-components`（4 个公共包）+ `devtools`（各应用接入面）
**审计日期**：2026-10-05
**基线文档**：`marschat-components/docs/README.md` · `CONFIG-REFERENCE.md` · `STATUS.md`（均截至 2026-09-19）
**审计方法**：文档通读 + 源码逐文件核对（含 diff 比对、全仓引用检索、行数实测），**结论均有命令取证，不含推测**

---

## 0. 结论

> **不满足。**
> 现状是 **「能力已组件化，接入面未收敛」**——4 个公共包把*能力*抽走了，但把*接入面*留给了每个应用。
> 新增一个应用仍需**手写约 1100 ~ 2300 行胶水代码**（实测），其中 60% 以上是同构复制粘贴，且**已因此产生过真实线上缺陷**。
>
> 「引入组件 + 少量配置化」只完成了前半句。后半句要补的是**装配层（App Kit / Starter）与脚手架**，不是再加文档。

## 2. 六个架构缺口（按严重度排序）

### 🔴 缺口 1（P1）后端 BFF 三件套未公共化，三份实现**行为已分叉**

`auth-core` 现有 17 个源文件，全部围绕「验签 / 鉴权 / 上报」：`TokenProvider`、`OidcTokenVerifier`、`@RequirePermission`、`MenuRegistryReporter`、`Feign` 透传。
**BFF 相关能力：0 个。**

于是每个应用各写一份：

| 类 | 副本数 | 行数 | diff 结果 |
|---|---|---|---|
| `AdminProxyController` | 3 | 297 / 295 / 266 | **语义相同，实现分叉**（见下） |
| `CenterSessionStore` | 2 | 71 / 71 | **除 `package` 行外逐字节相同** |
| `LocalAccountReporter` | 3 | 104 / 95 / 111 | 同构，字段/重试策略各异 |
| `SecurityConfig` | 6 | 38~70 | 各自手写，401 entry point 靠人记得加 |

**最严重的一处——同一语义两套凭据解析策略：**

```java
// kb-ops：直接透传调用者的 OIDC Authorization 头
String authHeader = request.getHeader("Authorization");
...
.header("Authorization", authHeader)

// infra-monitor：走 resolveCenterToken() 从 CenterSessionStore 取中心 token
String centerToken = resolveCenterToken(request);
...
.header("Authorization", "Bearer " + centerToken)
```

同一个「代理中心 `/admin/**`」语义，一个透传、一个换票。**这意味着安全边界不由架构保证，而由"当时抄的是哪一份"决定。** 白名单规则也各写各的（kb-ops 用 `Pattern` 常量 + `clientScopeOk` HPP 加固；infra 结构不同）。

> 这正是 `CenterSessionStore` 两份文件除包名外完全相同却仍存在两份的原因——**没有归属地**。它该在 `auth-core` 里。

### 🔴 缺口 2（P1）前端 Shell 未收敛：共享组件是死代码，各应用自建外壳

```
frontend-common/src/index.ts:34  export { default as SidebarMenu } from './components/SidebarMenu.vue'
```

**全仓检索 `SidebarMenu`（*.ts / *.vue / *.js，排除 node_modules）：0 处引用。**

各应用自己写侧边栏：

| 应用 | `MainLayout.vue` |
|---|---|
| kb-web | **675 行** |
| kb-ops | 307 行 |
| infra-monitor | 280 行 |

**后果**：三套外壳、三套交互、三套主题。`STATUS.md` 的 `T-LOW-11` 已登记「**三套外壳主题**、色语义重叠、低对比度（未授权态约 2.3:1）、框中框」共 16 项视觉债——**根因就是这里，不是"视觉待排期"**。

### 🟠 缺口 3（P2）菜单双份定义，靠人工对齐（违反「靠机制不靠承诺」）

同一个菜单在**两处**手写：

| 位置 | 形态 | 用途 |
|---|---|---|
| `kb-gateway/src/main/resources/menu-registry.yml` | 15 个 menu 节点 + 10 个 api 点 | 启动上报中心 → 生成权限点 |
| `kb-web/src/menus.ts` | `createKbMenus()` 15 个节点 | 前端渲染 + `useMenus` 过滤 |

`menu-registry.yml` 的注释自述：

> 菜单源 = kb-web src/menus.ts（createKbMenus，15 节点）；… 与 kb-web src/router/index.ts 的 permCode('menu','<key>') **严格对齐，禁止随意改名**

「严格对齐、禁止改名」= **靠人自觉**。改一处漏一处 → 菜单显示但点不动，或权限点存在但无入口。这个漂移**没有任何门禁能拦住**。

### 🟠 缺口 4（P2）兼容转发壳被当成了设计

各应用 `sso.ts` 均为 **16 个导出 / 126~168 行**，其中大部分不是适配，而是**为保持旧调用点不变的转发别名**：

```
startSsoLogin / handleSsoCallback / refreshOidcToken(@deprecated) / probeIdpSession
/ silentSignIn / bootstrapLoginPage / renewByReauthorize / buildSloUrl
/ startSessionWatcher / stopSessionWatcher / ssoLogout / clearLocalAuth / decodeOidcClaims
```

组件库 `index.ts` 已有 33 个导出，应用侧再包一层 16 个别名 → **双层 API 面**。文件头注释亦自认：

> 实现已全部收敛到公共组件；本文件只做两件事：1. 绑定自己的 OIDC 配置；2. **保持既有导出名与调用签名不变，上层零改动**

「上层零改动」是**迁移期**的正确取舍，但它被**固化了**——没有下线窗口，兼容层就变成了永久架构。真正的配置化接入应该是 `createMarschatApp()` 一次装配，而不是 16 个转发的文件。

### 🟠 缺口 5（P2）无脚手架、无模板：接入质量取决于「抄得全不全」

- `marschat-components/scripts/` 只有两个文件：`build-all.ps1`、`push-all.ps1` —— **零 scaffold**
- 官方接入路径 = 文档 Level 0~3 的手工清单（约 11 个前端文件 + 7 个后端文件），参考实现是「照抄 infra-monitor」

**这个机制已经出过事故。** `kb-web/src/utils/permissions.ts` 与 `infra-monitor-web` 的同名文件里留着这段注释：

> 🔴 必须传**路由内路径**：router 已带 /kb base，再拼 CONTEXT_PATH 会落 `/kb/kb/dashboard` … **kb-ops 早已修成 `/dashboard`，本处与 infra-monitor-web 是漏推广的两处**
> （infra 侧注：2026-09-14 **良哥实测** `monitor.marschat.online/infra/infra/services`）

即：kb-ops 修好的修复，**没有被推广到另外两处**，因为推广的机制是「人记得改」。缺陷现已修复，但**产生缺陷的机制原封不动**。

### 🟡 缺口 6（P3）portal 与其余 5 应用**不同构**

| 维度 | portal | 其余 5 应用 |
|---|---|---|
| Token 存储键 | `portal_token`（**非组件约定键**） | 组件约定键 + 应用前缀 |
| 换票路径 | 后端 BFF 换票（`SsoController` + `AuthCenterService`） | 前端直接 code 换票 |
| 会话监视器 | 必须显式注入 `getToken` / `clearLocalAuth`，否则**永不发探针** | 默认行为即可 |
| 会话类型 | 需区分 `oidc` / `legacy`（否则账密会话活不过 3 秒） | 单一路径 |

portal 的 `main.ts` 里那段「账密会话活不过 3 秒」的注释，本质是**共享组件的会话语义与 portal 的 BFF 语义不兼容**，只能靠调用方打补丁绕开。这类差异应该由装配层参数化（`sessionMode: 'bff' | 'oidc'`），而不是散落在宿主 `main.ts`。

## 3. 目标态架构：「三处配置 + 一行装配」

```
新增应用（目标）
├── 配置（3 份，全部为声明式）
│   ├── apps-registry.yml        ← 已存在（OIDC client + 前端运行时配置真源）  ✅
│   ├── menu-registry.yml        ← 已存在（菜单 + api 权限点真源）              ✅
│   └── bff-whitelist.yml        ← 新增（BFF 白名单，从 Java 常量外置）        ⬅ 待做
├── 前端装配（1 行）
│   └── main.ts:
│         createMarschatApp({ appId, router, menus, sessionMode: 'oidc' | 'bff' })
│         // 内部完成：运行时配置 → token 绑定 → SSO client → request + 401 分流
│         //           → 路由守卫 → 会话监视 → 权限预取 → 登录/回调/用户管理路由注册
└── 后端装配（1 行）
    └── @EnableMarschatAuth(appId = "marschat-xxx")
        // 自动配置：SecurityConfig(显式401) + OidcTokenVerifier + AdminProxyController(读 yml 白名单)
        //           + CenterSessionStore(可切 Redis) + LocalAccountReporter
```

**关键设计原则**：

1. **接入面下沉到包内，应用只保留"业务数据"**（菜单、权限点、白名单）——业务数据本来就是声明式的，天然可配置化。
2. **消灭双份定义**：`menus.ts` 由 `menu-registry.yml` **生成**（同一份真源，一个生成器），或反过来让前端直接消费 yml。二者必居其一，不能手写两份。
3. **BFF 白名单配置化**：`isAllowed()` 的 30 行硬编码 → `bff-whitelist.yml` 的路径列表，由 starter 读取。新增中心端点=改配置，不是改 3 份 Java。
4. **兼容层设下线窗口**：16 个别名标注移除版本（如 0.9.0），到期强制清理，避免「迁移遗留」永久化。

## 4. 分阶段改造路线

| 阶段 | 内容 | 收益 | 风险 |
|---|---|---|---|
| **P0**（1 周） | ① 3 份 `AdminProxyController` 收敛为 `auth-core` 的 `AdminProxyAutoConfig`，白名单外置 `bff-whitelist.yml`<br>② 2 份 `CenterSessionStore` 上移 `auth-core`<br>③ 3 份 `LocalAccountReporter` 合并（差异参数化） | 消除**安全边界分叉**（最高危）；应用后端胶水 **-400~600 行/应用** | 中：BFF 是安全边界，需逐应用真浏览器回归（走 `webapp-e2e-verify` 口径） |
| **P1**（1~2 周） | ① `menus.ts` 由 `menu-registry.yml` 生成，消灭双份定义<br>② `SidebarMenu` 落地或删除（**不允许既导出又零引用**）<br>③ `MainLayout.vue` 收敛为共享 `AppShell` | 菜单漂移归零；三套外壳 → 一套；`T-LOW-11` 视觉债根因消除 | 低：前端可灰度，一应用一应用切 |
| **P2**（2~3 周） | ① 前端 `@marschat/app-kit`：`createMarschatApp()` 装配层 + `pnpm create marschat-app` 脚手架<br>② 兼容别名设下线版本并清理<br>③ portal 的 BFF 语义参数化（`sessionMode`） | 新应用接入从 ~1500 行降到 **< 100 行**；「照抄 infra-monitor」模式退役 | 中：涉及 portal 会话链路，需 SLO/免登/账密三条通道回归 |

**顺序不可颠倒**：P0 是安全边界，P2 是体验优化。先堵安全分叉，再谈开发效率。

## 5. 代码质量把控机制（把规范从文档搬进 CI）

当前接入规范**全部写在文档里**（README Level 4 的 A~E 五组 checklist，靠人打勾）。这是「靠承诺」。建议改为**门禁**：

| 门禁 | 检查内容 | 工具 |
|---|---|---|
| **接入合规检查** | ① `SecurityConfig` 有显式 401 entry point ② `issuer` 与签发方逐字一致 ③ `menu-registry.yml` 有且仅有 1 个 `public: true` ④ 无本地密码校验/双写 ⑤ BFF 白名单存在且非空 | 自研 lint 脚本，纳入各应用流水线 |
| **重复代码门禁** | 应用侧同构文件（`sso.ts`/`permissions.ts`/`AdminProxyController`）相似度阈值告警 | `jscpd`（前端）+ `PMD CPD`（后端） |
| **依赖方向门禁** | 禁止应用自建密码体系；禁止绕过公共包直连中心域名 | `ArchUnit`（后端）+ ESLint 自定义规则（前端） |
| **契约测试** | 组件发版时自动跑 6 应用接入面回归（免登/账密/401/闸门/SLO 五条通道） | 现有 Phase 12 回归脚本，收敛为仓库内单一入口（`T-REG-1`） |
| **版本三对齐** | `package.json` 约束 + lock + 线上版本戳一致（坑 #13）；UMD 版本戳 == 产物内 `version` 常量（`T-LOW-3`） | CI 脚本 |

**优先级建议**：`重复代码门禁` 与 `接入合规检查` 先上——它们成本最低，且直接拦住本报告 §2 中已经发生过的两类事故（漂移缺陷、安全边界分叉）。
